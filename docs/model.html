Why it's shaped this way

  • A session owns its workspace. The workspace is what a session needs to work on its issue: a checkout of the project on the instance's node, on the session's own branch. It is made when the session starts and removed with the session.
  • Each turn records a snapshot commit on the session's branch. Unchanged turns may share a commit, and per-turn diffs compare consecutive recorded snapshots. Historical undo is unavailable.
  • A harness is shared by every instance of it; it comes with the binary as plugin data. An instance is one harness on one node with one account, so a node can run the same harness on two accounts, e.g. a subscription and an API key.
  • A session is an instance working on an issue, at most one per pair, so two sessions of one instance never race on one issue. The harness's own id for the conversation is the harness's bookkeeping, kept by its plugin in the session's workspace, not part of the model.
  • None of the owner's own names is a key. Projects are keyed by ids that never change, so they can be renamed; nodes by their public key. An instance's account is named by its harness and provider, not by the owner, so it is a stable part of the instance's key.
  • A project's root commit is unique to it and is how a node recognises its copy whatever the remote or path; it is not the key, because a fork or a templated repository shares it. Its default branch is git's, not the model's.
  • A session has its own branch, cut from its issue's branch, because a branch can be checked out in only one place. What a session does reaches the issue by landing its branch on the issue's branch.
  • A session is keyed by its issue and its instance; its node and project follow from those, so nothing can disagree.
  • Sub-agents are part of a session, like a tool call, so they can't point at another issue. There are no sub-issues.
  • A node has at most one copy of a project; workspaces are made from it. The home never records where a node keeps it: a node finds it by root commit and remote.
  • Pairing and Copy invent no ids: each is keyed by what it relates.

Rules the structure doesn't show

  • Every session belongs to an issue; a quick, unplanned session gets an issue made for it.
  • A session's instance runs on a node that has a copy of its issue's project.
  • Continuing an issue starts a new session from its branch and notes. Select Finish and check that the issue branch was pushed before continuing its landed work on another node with a project checkout.
